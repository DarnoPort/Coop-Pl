# Проверки

## Автоматические проверки

В PowerShell из корня репозитория:

    cd server
    npm.cmd install
    npm.cmd test

Тесты находятся в соседнем каталоге tests/, а зависимость ws устанавливается в server/node_modules/. Интеграционный тест явно разрешает ws относительно каталога пакета сервера, поэтому установка зависимости в этом пакете работает и в Windows.

Синтаксическую проверку плагина, находясь в каталоге server, запускай так:

    node --check ../plugin/CoopPl_Core.js

Скрипт tests/protocol.test.js проверяет валидацию пакетов, tests/server.test.js запускает настоящий WebSocket-сервер и двух WebSocket-клиентов, а tests/plugin.test.js загружает плагин в минимальный mock-runtime RPG Maker для проверки базового цикла подключения и remote sprite. Эти проверки не заменяют запуск двух настоящих экземпляров MZ.

## Подготовка двух тестовых сборок из одного экспорта\n\nБольше не нужно вручную вносить одинаковые изменения в два исходных проекта и отдельно настраивать оба package.json. Подготовь один Windows deployment из одного исходного проекта, затем запусти helper из корня репозитория:\n\n    node tools/prepare-test-builds.js --source "D:\\Path\\To\\WindowsExport" --output "D:\\Coop-Pl-Test\\Builds" --server-url "ws://127.0.0.1:8080" --room-code "TEST_ROOM"\n\nЗамени Source и Output на свои реальные каталоги. Source должен быть папкой Windows-сборки с Game.exe и package.json; helper поддерживает стандартную структуру MZ с игровыми файлами в www/.\n\nСкрипт создаст:\n\n    <output>\\Host\\Game.exe\n    <output>\\Guest\\Game.exe\n\nОн копирует один экспорт в два каталога, устанавливает актуальный CoopPl_Core.js, включает плагин, выставляет одному клиенту имя Host, другому Guest, сохраняет общий URL/код комнаты и задаёт уникальный --user-data-dir каждой сборке. Исходный экспорт не изменяется.\n\nКаждый новый проектный экспорт сначала подготавливается этим скриптом. Если в Output уже существуют папки Host или Guest, скрипт откажется их перезаписывать: укажи новый Output или удали только старые сгенерированные тестовые папки после проверки пути.\n\nНе используй helper для единственной production-сборки или для папки исходного проекта. Это инструмент разработки и тестирования.\n\n## Если вторая игра MZ сразу закрывается

**Не редактируй проектный package.json как постоянное исправление.** RPG Maker MZ может пересоздать его при открытии или сохранении проекта, поэтому ручные изменения пропадут. Вместо этого меняй `package.json` в двух экспортированных Windows-сборках и запускай именно их.

В сообществе RPG Maker описан обходной путь: задать NW.js/Chromium отдельный профиль с параметром `--user-data-dir`. Это практический совет сообщества, а не официальная настройка совместной игры: https://www.reddit.com/r/RPGMaker/comments/13glogd/opening_multiple_games_at_the_same_time/.

### Правильный порядок

1. В исходном проекте включи `CoopPl_Core` через Plugin Manager, сохрани проект и закрой редактор.
2. Через **Deployment → Windows** создай две сборки в разных папках, например `D:\\Coop-Pl-Test\\Host` и `D:\\Coop-Pl-Test\\Guest`. Убедись, что выбран обычный Windows deployment.
3. Открой `package.json` рядом с `Game.exe` в папке Host. Найди существующее свойство `chromium-args`; если его нет, добавь новое свойство верхнего уровня. Укажи хосту отдельный путь профиля:
   
       "chromium-args": "--force-color-profile=srgb --user-data-dir='.\\\\nwjs-profile-host'"

4. В сборке Guest аналогично укажи другой каталог:

       "chromium-args": "--force-color-profile=srgb --user-data-dir='.\\\\nwjs-profile-guest'"

5. Если в сгенерированном `package.json` уже есть другие аргументы в `chromium-args`, сохрани их и допиши `--user-data-dir=...`, не создавай дубликат поля. Соблюдай JSON-синтаксис: запятые обязательны между свойствами.
6. Больше не открывай эти папки как проекты в редакторе и не выполняй Deployment повторно поверх них: повторная сборка может перезаписать изменённый файл. Открывай непосредственно `Game.exe` из каждой папки.

Официальная справка описывает запуск Windows-сборки через `Game.exe` в папке развёрнутой игры: https://rpgmakerofficial.com/product/MZ_help-en/01_06.html.

### Проверка

Полностью закрой ранее запущенные тестовые игры и проверь в Диспетчере задач, что их процессы завершились. Запусти Coop-Pl server, затем `Host\\Game.exe`, после него `Guest\\Game.exe`. В серверной консоли должны появиться две записи подключения к одной комнате.

Изменение профиля должно сохраняться в экспортированной сборке, потому что редактор MZ больше не должен переписывать её `package.json`. После каждой новой сборки этот шаг нужно выполнить заново, если ты не автоматизировал постобработку.

Это обходной путь для тестовой среды, а не исправление Coop-Pl и не гарантия, что он устранит любую причину закрытия второй игры. Если проблема останется, проверь, появляется ли второй процесс в Диспетчере задач и есть ли сообщения об ошибках в консоли разработчика (F8 в режиме Playtest).

## Запуск сервера локально

Требуется Node.js 20 или новее.

    cd server
    npm install
    npm start

Сервер по умолчанию слушает 127.0.0.1:8080. Для доступа с другого компьютера в доверенной локальной сети запусти его явно с привязкой ко всем интерфейсам.

PowerShell:

    $env:COOP_HOST = "0.0.0.0"
    $env:COOP_PORT = "8080"
    npm start

Для подключения двух копий на одном компьютере используй ws://127.0.0.1:8080 в параметре ServerUrl. Для второго компьютера в той же LAN используй ws://<LAN-IP-хоста>:8080 и разреши входящий порт в Windows Firewall, если он заблокирован.

Не выставляй сервер в публичный Интернет: сейчас нет шифрования или аутентификации.

## Тест в RPG Maker MZ

1. Сделай копию проекта, не тестируй на единственном оригинале.
2. Скопируй plugin/CoopPl_Core.js в копию проекта, в js/plugins/.
3. В Plugin Manager включи CoopPl_Core. Параметр SyncSwitchesVariables должен быть включён.
4. В Database добавь хотя бы один переключатель, например COOP_TEST_SWITCH, и одну переменную, например COOP_TEST_VALUE. Сервер и плагин не смогут синхронизировать ID, которого нет в базе игры.
5. Для обеих копий укажи один ServerUrl и RoomCode, но разные PlayerName.
6. Запусти сервер, затем обе экспортированные копии игры.
7. Проверяй только после подтверждённого сообщения connected в игровом логе и появления удалённого персонажа.

### Отдельный тест общих переключателей и переменных

Сделай временное тестовое событие с триггером Action Button. Внутри него добавь только обычные event commands:

1. Control Switches: включить COOP_TEST_SWITCH.
2. Control Variables: установить COOP_TEST_VALUE в число 123.

На той же карте создай второе, отдельное событие-индикатор: на первой странице оно имеет обычную графику, а на второй странице поставь условие COOP_TEST_SWITCH ON и используй другую графику. Не запускай индикатор через Autorun или Parallel.

На клиенте-госте нажми первое событие один раз. Проверяй, что:

- на хосте также включился COOP_TEST_SWITCH;
- на хосте значение COOP_TEST_VALUE стало 123;
- индикатор переключил страницу на обеих играх;
- команды не продолжают многократно отправляться в сетевой цикл.

Если один пункт не выполняется, пришли журнал сервера и ошибки F8 из обеих игр. Для отдельной проверки наград см. следующий раздел: предметы/золото/состояние актёров передаются снимком после завершения общего события, а не как единая атомарная транзакция.

Важно: общие события исполняются на хосте. Гость пока не видит диалоговые окна и выборы из этого event interpreter. Не включай в этот тест бои или переходы карты: они пока не синхронизируются как единый игровой процесс.

### Условия PASS для сетевого прототипа

- Оба клиента подключаются к той же комнате.
- Каждый клиент видит другого игрока на той же карте.
- Движение и направление обновляются без постоянного дублирования персонажей.
- После выхода одного клиента у другого исчезает его sprite.
- Повторное подключение не оставляет фантомного игрока.
- Переход игрока на другую карту не показывает его sprite на неправильной карте.
- Ошибка сервера или отключение не приводит к зависанию игрового цикла.

До выполнения этого теста статус интеграции остаётся непроверенным.


## Ручная проверка снимка группы в настоящем RPG Maker MZ

Этот тест нужен после автоматических проверок: он проверяет взаимодействие с настоящими \`Game_Party\`, \`Game_Actor\` и сменой страниц событий. Тестируй только в копии проекта, не в рабочем сохранении.

1. Обнови плагин из этой ветки, сделай один Windows-экспорт и подготовь парные сборки по команде выше. Запусти сервер и сначала Host, затем Guest; убедись, что оба вошли в одну комнату и стоят на одной карте.
2. На временной тестовой карте создай событие с триггером **Action Button**. В списке команд расположи: **Show Text** (напиши «Host event start»), **Change Items** (Potion +1), **Change Gold** (+50), **Change HP** (выбери живого участника и снизь HP на 5), затем **Control Self Switch A = ON**.
3. Добавь вторую страницу того же события с условием **Self Switch A is ON** и поменяй графику события или поставь другой комментарий. Это позволяет увидеть синхронизацию self-switch отдельно от снимка группы.
4. На Guest нажми на событие один раз и дождись, пока событие полностью закончится на Host. В текущем этапе текст появится только на Host — это ожидаемое ограничение, не провал теста.
5. После завершения события проверь на Guest меню предметов и золото, статус выбранного актёра (HP), а также вторую страницу события. На обоих клиентах должны быть +1 Potion, +50 золота, одинаковое уменьшение HP и включённый self-switch A. Повтори вход третьего клиента, если хочешь убедиться, что актуальный снимок группы передаётся и новому участнику.

**PASS:** после окончания события значения группы совпадают на Host и Guest, и страница переключилась на обоих клиентах.

**FAIL:** если хотя бы одно значение отличается, Guest не получает снимок после завершения события или событие срабатывает дважды, пришли: (1) содержимое списка команд тестового события, (2) вывод \`CoopPl.status()\` из F8 на обоих клиентах, (3) журнал окна сервера и ошибки из F8.

Не тестируй на этом этапе событие, в котором после выдачи предмета сразу проверяется инвентарь и выбирается сюжетная ветка: проверка во время исполнения ещё может дать разные результаты, потому что снимок применяется только после завершения события.
