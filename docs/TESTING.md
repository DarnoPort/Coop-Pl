# Проверки

## Автоматические проверки

В PowerShell из корня репозитория:

    cd server
    npm.cmd install
    npm.cmd test

Тесты находятся в соседнем каталоге tests/, а зависимость ws устанавливается в server/node_modules/. Интеграционный тест явно разрешает ws относительно каталога пакета сервера, поэтому установка зависимости в этом пакете работает и в Windows.

Синтаксическую проверку плагина, находясь в каталоге server, запускай так:

    node --check ../plugin/CoopPl_Core.js

Скрипт tests/protocol.test.js проверяет валидацию пакетов, tests/server.test.js запускает настоящий WebSocket-сервер и двух WebSocket-клиентов, а tests/plugin.test.js загружает плагин в минимальный mock-runtime RPG Maker для проверки базового цикла подключения и remote sprite. Эти проверки не заменяют запуск двух настоящих экземпляров MZ.

## Подготовка двух тестовых сборок из одного экспорта

Больше не нужно вручную вносить одинаковые изменения в два исходных проекта и отдельно настраивать оба package.json. Подготовь один Windows deployment из одного исходного проекта, затем запусти helper из корня репозитория:

    node tools/prepare-test-builds.js --source "D:\\Path\\To\\WindowsExport" --output "D:\\Coop-Pl-Test\\Builds" --server-url "ws://127.0.0.1:8080" --room-code "TEST_ROOM"\n\nЗамени Source и Output на свои реальные каталоги. Source должен быть папкой Windows-сборки с Game.exe и package.json; helper поддерживает стандартную структуру MZ с игровыми файлами в www/.\n\nСкрипт создаст:\n\n    <output>\\Host\\Game.exe\n    <output>\\Guest\\Game.exe\n\nОн копирует один экспорт в два каталога, устанавливает актуальный CoopPl_Core.js, включает плагин, выставляет одному клиенту имя Host, другому Guest, сохраняет общий URL/код комнаты и задаёт уникальный --user-data-dir каждой сборке. Исходный экспорт не изменяется.\n\nКаждый новый проектный экспорт сначала подготавливается этим скриптом. Если в Output уже существуют папки Host или Guest, скрипт откажется их перезаписывать: укажи новый Output или удали только старые сгенерированные тестовые папки после проверки пути.\n\nНе используй helper для единственной production-сборки или для папки исходного проекта. Это инструмент разработки и тестирования.\n\n## Если вторая игра MZ сразу закрывается

**Не редактируй проектный package.json как постоянное исправление.** RPG Maker MZ может пересоздать его при открытии или сохранении проекта, поэтому ручные изменения пропадут. Вместо этого меняй `package.json` в двух экспортированных Windows-сборках и запускай именно их.

В сообществе RPG Maker описан обходной путь: задать NW.js/Chromium отдельный профиль с параметром `--user-data-dir`. Это практический совет сообщества, а не официальная настройка совместной игры: https://www.reddit.com/r/RPGMaker/comments/13glogd/opening_multiple_games_at_the_same_time/.

### Правильный порядок

1. В исходном проекте включи `CoopPl_Core` через Plugin Manager, сохрани проект и закрой редактор.
2. Через **Deployment → Windows** создай две сборки в разных папках, например `D:\\Coop-Pl-Test\\Host` и `D:\\Coop-Pl-Test\\Guest`. Убедись, что выбран обычный Windows deployment.
3. Открой `package.json` рядом с `Game.exe` в папке Host. Найди существующее свойство `chromium-args`; если его нет, добавь новое свойство верхнего уровня. Укажи хосту отдельный путь профиля:
   
       "chromium-args": "--force-color-profile=srgb --user-data-dir='.\\nwjs-profile-host'"

4. В сборке Guest аналогично укажи другой каталог:

       "chromium-args": "--force-color-profile=srgb --user-data-dir='.\\nwjs-profile-guest'"

5. Если в сгенерированном `package.json` уже есть другие аргументы в `chromium-args`, сохрани их и допиши `--user-data-dir=...`, не создавай дубликат поля. Соблюдай JSON-синтаксис: запятые обязательны между свойствами.
6. Больше не открывай эти папки как проекты в редакторе и не выполняй Deployment повторно поверх них: повторная сборка может перезаписать изменённый файл. Открывай непосредственно `Game.exe` из каждой папки.

Официальная справка описывает запуск Windows-сборки через `Game.exe` в папке развёрнутой игры: https://rpgmakerofficial.com/product/MZ_help-en/01_06.html.

### Проверка

Полностью закрой ранее запущенные тестовые игры и проверь в Диспетчере задач, что их процессы завершились. Запусти Coop-Pl server, затем `Host\\Game.exe`, после него `Guest\\Game.exe`. В серверной консоли должны появиться две записи подключения к одной комнате.

Изменение профиля должно сохраняться в экспортированной сборке, потому что редактор MZ больше не должен переписывать её `package.json`. После каждой новой сборки этот шаг нужно выполнить заново, если ты не автоматизировал постобработку.

Это обходной путь для тестовой среды, а не исправление Coop-Pl и не гарантия, что он устранит любую причину закрытия второй игры. Если проблема останется, проверь, появляется ли второй процесс в Диспетчере задач и есть ли сообщения об ошибках в консоли разработчика (F8 в режиме Playtest).

## Запуск сервера локально

Требуется Node.js 20 или новее.

    cd server
    npm install
    npm start

Сервер по умолчанию слушает 127.0.0.1:8080. Для доступа с другого компьютера в доверенной локальной сети запусти его явно с привязкой ко всем интерфейсам.

PowerShell:

    $env:COOP_HOST = "0.0.0.0"
    $env:COOP_PORT = "8080"
    npm start

Для подключения двух копий на одном компьютере используй ws://127.0.0.1:8080 в параметре ServerUrl. Для второго компьютера в той же LAN используй ws://<LAN-IP-хоста>:8080 и разреши входящий порт в Windows Firewall, если он заблокирован.

Не выставляй сервер в публичный Интернет: сейчас нет шифрования или аутентификации.

## Тест в RPG Maker MZ

1. Сделай копию проекта, не тестируй на единственном оригинале.
2. Скопируй plugin/CoopPl_Core.js в копию проекта, в js/plugins/.
3. В Plugin Manager включи CoopPl_Core. Параметр SyncSwitchesVariables должен быть включён.
4. В Database добавь хотя бы один переключатель, например COOP_TEST_SWITCH, и одну переменную, например COOP_TEST_VALUE. Сервер и плагин не смогут синхронизировать ID, которого нет в базе игры.
5. Для обеих копий укажи один ServerUrl и RoomCode, но разные PlayerName.
6. Запусти сервер, затем обе экспортированные копии игры.
7. Проверяй только после подтверждённого сообщения connected в игровом логе и появления удалённого персонажа.

### Отдельный тест общих переключателей и переменных

Сделай временное тестовое событие с триггером Action Button. Внутри него добавь только обычные event commands:

1. Control Switches: включить COOP_TEST_SWITCH.
2. Control Variables: установить COOP_TEST_VALUE в число 123.

На той же карте создай второе, отдельное событие-индикатор: на первой странице оно имеет обычную графику, а на второй странице поставь условие COOP_TEST_SWITCH ON и используй другую графику. Не запускай индикатор через Autorun или Parallel.

На клиенте-госте нажми первое событие один раз. Проверяй, что:

- на хосте также включился COOP_TEST_SWITCH;
- на хосте значение COOP_TEST_VALUE стало 123;
- индикатор переключил страницу на обеих играх;
- команды не продолжают многократно отправляться в сетевой цикл.

Если один пункт не выполняется, пришли журнал сервера и ошибки F8 из обеих игр. Для отдельной проверки наград см. следующий раздел: предметы/золото/состояние актёров передаются снимком после завершения общего события, а не как единая атомарная транзакция.

Важно: общие события исполняются на хосте. Show Text отображается и у гостя; Show Choices передаёт варианты, но решение принимает только хост. После получения результата гостевое окно выбора автоматически закрывается, без дополнительного Enter. Не включай в этот тест бои или переходы карты: они пока не синхронизируются как единый игровой процесс.

### Условия PASS для сетевого прототипа

- Оба клиента подключаются к той же комнате.
- Каждый клиент видит другого игрока на той же карте.
- Движение и направление обновляются без постоянного дублирования персонажей.
- После выхода одного клиента у другого исчезает его sprite.
- Повторное подключение не оставляет фантомного игрока.
- Переход игрока на другую карту не показывает его sprite на неправильной карте.
- Ошибка сервера или отключение не приводит к зависанию игрового цикла.

До выполнения этого теста статус интеграции остаётся непроверенным.


## Ручная проверка Show Text и Show Choices в настоящем RPG Maker MZ

Тестируй только в копии проекта и на временной карте. Обнови плагин из ветки, сделай один Windows-экспорт и подготовь две сборки Host/Guest по инструкции выше. Запусти сервер, затем Host и Guest; оба клиента должны быть в одной комнате и на одной карте.

### Show Text

1. Создай Action Button event с двумя последовательными командами Show Text, например «Первая строка» и «Вторая строка». Можно задать лицо, фон и позицию окна.
2. Активируй событие на Guest. Обе игры должны показать текст в правильном порядке; закрой сообщения и дождись окончания события на Host.
3. Если у Guest уже открыто другое локальное сообщение, входящий общий текст должен ждать своей очереди, а не прерывать его. Сначала проще проверить при свободных окнах.

### Show Choices — решение хоста

1. Создай отдельное Action Button event: Show Text, затем Show Choices с вариантами «Остаться» и «Уйти». В ветке «Остаться» включи переключатель \`COOP_STAY\`, в ветке «Уйти» — \`COOP_LEAVE\`. После каждой ветки добавь свой Show Text. Переключатели заранее создай в Database.
2. На Guest активируй событие. Оба клиента должны увидеть одинаковый текст и список вариантов.
3. Пока Host не выбрал вариант, на Guest попробуй нажимать стрелки, Enter и выбирать мышью. Гость не должен подтвердить собственную ветку или изменить решение хоста.
4. На Host выбери «Уйти». На Guest решение хоста не должно заменяться локальным. Если у Guest ещё открыто предыдущее сообщение, нажми Enter, чтобы закрыть именно его; окно выбора гостя должно автоматически подтвердить решение хоста и не требовать второго Enter.
5. После завершения события проверь, что \`COOP_LEAVE\` включён у обоих клиентов, а \`COOP_STAY\` выключен. Повтори с выбором «Остаться». Если отмена разрешена настройками Show Choices, отдельно проверь её.

**PASS:** Guest видит общие варианты, не может навязать свой результат, получает решение хоста, а итоговое состояние переключателей одинаковое.

**FAIL:** у Guest можно независимо выбрать другую ветку, не отображается результат Host, гостевое окно застревает или отличаются переключатели. Пришли список команд события, \`CoopPl.status()\` из F8 обоих клиентов и ошибки из F8/серверного окна.

### Снимок группы после общего события

1. На временной карте создай Action Button event с командами: Show Text «Host event start», Change Items (Potion +1), Change Gold (+50), Change HP (уменьшить HP живого актёра на 5), Control Self Switch A = ON.
2. Добавь вторую страницу того же события с условием Self Switch A is ON и другой графикой.
3. Активируй событие на Guest и дождись завершения на Host. Текст должен появиться на обоих клиентах.
4. После завершения проверь на Guest предметы, золото, HP выбранного актёра и вторую страницу события. Ожидаются +1 Potion, +50 золота, одинаковое изменение HP и Self Switch A на обоих клиентах.

**PASS:** значения группы и self-switch совпадают после завершения события, событие не исполняется дважды.

**FAIL:** пришли список команд события, \`CoopPl.status()\` с обоих клиентов, журнал сервера и ошибки F8.

Это всё ещё не тестирует полную синхронизацию игры. Хост один исполняет ветку выбора; снимок инвентаря/золота/HP применяется на Guest после завершения события, а не после каждой команды. Не включай в эти тесты бои, движение событий или переходы карты.


## Фоновое окно Host/Guest

В новой версии `tools/prepare-test-builds.js` тестовые сборки получают Chromium/NW.js-флаги `--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows`. Они уменьшают фоновое ограничение кадров/таймеров, из-за которого сообщения события могли появляться только после переключения на окно игры. Это настройка тестовой сборки, а не часть самого плагина.

Если Host/Guest уже созданы старой версией helper, одной заменой `CoopPl_Core.js` новые параметры не добавятся. Для каждого существующего экспорта открой `package.json`, найди `chromium-args` и добавь эти три флага, сохранив имеющиеся параметры и отдельный `--user-data-dir` хоста/гостя. Полностью закрой и заново запусти обе игры. При новой подготовке пары helper добавит флаги автоматически.

## Проверка движения событий у Host/Guest

1. На временной карте создай событие с графикой (например, NPC), которое можно однозначно видеть на обеих играх. Убедись, что ID событий и содержимое карт совпадают у Host и Guest.
2. Создай отдельное событие с триггером Action Button. Добавь команду Set Movement Route, укажи в качестве цели NPC и задай маршрут из нескольких шагов (например, вправо, вправо, вниз). Включи Wait for Completion, а после маршрута покажи текст `Маршрут завершён`.
3. Активируй событие через Guest. Хост должен исполнить событие один раз. NPC у гостя должен визуально следовать за хостом и прийти на тот же конечный тайл; у гостя не должно запускаться самостоятельное параллельное событие для этого NPC.
4. Повтори тест с событием, помеченным комментарием `<CoopLocal>`. Его движение должно остаться локальным и не перезаписываться сетевым снимком.

**PASS:** положение NPC, направление и базовая графика совпадают после маршрута; локальные события не меняются из-за сетевых снимков.

Это пока синхронизация состояния/позиции, а не полная репликация маршрута: точное покадровое время, столкновения и условия, которые зависят от игровой логики, не гарантируются. Переходы между картами этим этапом ещё не синхронизированы.

## Тайминг Show Text и Show Choices

Каждый клиент отдельно закрывает своё окно текста. Если Host уже выбрал вариант, пока Guest ещё читает предыдущее сообщение, Guest сначала должен закрыть именно это сообщение. Когда очередь дойдёт до выбора, плагин применит результат Host и автоматически закроет неинтерактивное окно выбора — второй Enter для него не нужен. Гость не запускает ветку самостоятельно: команды выбранной ветки исполняет только Host. Если после результата хоста Guest зависает на выборе или получает другой результат, это ошибка синхронизации.
